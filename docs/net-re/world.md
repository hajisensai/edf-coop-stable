# 联机：敌人、子弹与任务事件（W4 静态逆向）

EDF.dll TimeDateStamp `0x678CCB46`，下文地址全部是 RVA。纯静态分析（capstone + all-forces 仓的 `tools/edfre.py`），没有起游戏，也没有两机实测。
置信度：**H** = 指令里直接读到；**M** = 有代码证据的推断；**L** = 推测，要实机确认。
`obj+X` 指对象（GameObjectBase 派生类）偏移；`NetObj` 是对象里 `+0x120` 处的 `net::NetworkObject` 子对象，`NetObj+X` = `obj+0x120+X`。

一句话结论：**原版敌人是「每台机器都完整模拟、注册拥有者定期校正」**。任务脚本生成的敌人拥有者是房主；拥有者发位姿、随机数状态、攻击目标，
任务脚本的等待条件只在房主求值、由房主广播唤醒。**最大的分歧点是目标重选**：每台机器每 60 帧都按自己看到的位置重选最近的敌方，
远端副本会覆盖拥有者发来的目标（§5）。本分支已修这一点（§7）。

## 1. 网络注册族

### 1.1 `0x7834F0`：任务脚本生成（H）

`0x7834F0(mgr, weak_ptr<obj>, byte remoteOwned, int key, int, float)`：

- 网络 ID 由 `0x7772D0(&id, key)` 构造：`dword[0] = key`，其余清零（类型字段 `+0xC = 0`），再 `0x776450` 对整个 ID 做 FNV-1a 哈希。
- `0x782720 → 0x782880` 入表，`NetworkObject+8` 置 bit0 = remoteOwned、bit1 = !remoteOwned（`0x782945..0x782976`）。
- 调用者全是任务脚本 VM（`MissionScriptBVMImplement`，vtable `0x179D2A0` slot 0 `0x20FF70`）的原生函数：`0x1DE348`、`0x1DED8E`、`0x215120`、
  `0x2154C0`、`0x216E90`、`0x217C20`、`0x2181E0`、`0x218650`、`0x2191B0`、`0x219720`、`0x21A290`、`0x21B517`、`0x21B590`、`0x21BB40`、`0x21C4A0`、
  `0x21E0D0`、`0x22AB90`。
- 以 `0x2154C0` 为例：`remoteOwned = 0x784120()`（**IsGuest**：在房间里且本机不是房主，`0x78417B` 调 `0x734F00` 比较成员）。所以**任务脚本生成
  的对象在房主上 bit1（本机的），在客人上 bit0（别人的）：拥有者是房主**。（H）
- `key = 0x10AC6E0(vm+0x70)` = 脚本 VM 当前指令指针相对字节码起点的偏移（`0x10AC6E0`：`[ctx+0xE0] - [[ctx]+8]`）。即**网络 ID = 生成这条脚本语句
  的字节码位置**。（H 代码 / M：同一语句在循环里多次生成时，表内如何区分同 ID 没有读完，`0x782880` 的入表逻辑未逐条分析，L）
- 客人这边若对象是 GameObjectBase，还调 `0x54EDB0`（`obj+0x338 = -1`、`+0x340 = 0`、清 `+0x348`）。用途未查（L）。

### 1.2 `0x781630`：敌人派生的子对象（H）

`0x781630(mgr, weak_ptr<obj>, weak_ptr<parent>, int index, int sub, byte remoteOwned)`：

- ID = `0x7766B0(&id, 0x784A10(parent), index, sub)`：`u16 index, u16 sub, u32 父对象网络身份的哈希`（`0x776AB0`），类型 `+0xC = 4`。
  `0x784A10` 把 parent `dynamic_cast` 成 `net::NetworkObject`（类型描述符 `0x200CB20`）取它的身份。
- 调用者 remoteOwned 都是**父对象 `+0x128 & 1`**（`0x4F5086`、`0x6D0354`、`0x775E1E`、`0x413604` 等）：**子对象跟随父对象的拥有者**。
- 调用者（不是 online-re 猜的「敌人本体」）：DeiroiFallEffect（`0x323D10`）、DeiroiFootParts（`0x327B60`）、Berserker_Middle/TypeShooter（`0x3511C0`
  经 `0x37DAB0`）、Jormungand 外星头部件（`0x3993C0`）、GiantAntEgg 孵化（`0x4134E0`）、BigGreyBoss 陨石与武器（`0x44BCD0`、`0x474F90`）、
  MovingFortress（`0x4C79C0`）、DropBoat512 卸货（`0x4F4C90`）、Bullet_TypeBullet / TypeEntityBullet slot 1（`0x6D02B0`）、通用生成助手
  `0x775C70/0x775F00`（AntHill、TimeShip_Anchor/Capsule、生成器）。

结论（H）：**敌人本体由任务脚本经 `0x7834F0` 注册（房主拥有）；巢穴、蛋、运输船、Boss 放出的东西经 `0x781630` 注册，拥有者 = 父对象的拥有者
（通常也是房主）**。每台机器各自 `CreateObject`，靠可推导的 ID 绑定，和 online-re §2 的载具投送是同一个思路。

## 2. 敌人状态复制

### 2.1 NetworkObject 虚表约定（H）

基类 `net::NetworkObject` vtable `0x176A588`：slot 5 默认跳 slot 7、slot 6 默认跳 slot 8；slot 7 默认 `0x125A80`（返回 0，无数据）、slot 8 默认
`0x125190`（空）；slot 14 `0x773B50` = 发送（online-re 的「vtable +0x70」）；slot 15 / 17 = 消息接收。GameObjectBase 的 NetObj vtable `0x17CD560`：
slot 15 `0x54D590`、slot 17 `0x54D770`、slot 20 `0x549130`。

### 2.2 虫类（GiantAnt / EX、Bee、Spider；InsectBase）（H）

GiantAnt NetObj vtable `0x17BB990`：slot 5 `0x40C510`（写）、slot 6 `0x408400`（读）、slot 7 `0x4AA550`（帧计数 `NetObj+0x10A0` 加一）、slot 15 `0x40BB10`
（消息，未处理的交 `0x4A9FF0` → `0x54D590`）。

**写（`0x40C510`）**只在 `NetObj+8 & 1 == 0`（本机拥有）时组掩码：

| 位 | 条件 | 内容（对象偏移） |
|---|---|---|
| 1 | 帧计数 % 周期 == 0 且有变化（`+0x1FF0`），或 `+0x1FC0 & 5 == 5` 立即 | `obj+0x1F60` 的 `net::WalkCharacterSyncControl`（写 `0x77D500`）：标志字节、1 字节、**位置 vec3、压缩四元数**；**不带速度** |
| 2 | 计数器 `obj+0x1F21` | 1 字节事件 |
| 0x80 | 计数器 `obj+0x1F30` | `obj+0x1F40`（`+0x5C8==1` 时）+ u64 `obj+0x1F50` |
| 8 | 每 6 帧 | 三个状态等级（`+0x1640/+0x1644/+0x1648`）+ `+0x1F18` |
| 0x10 / 0x20 | 每 80 帧，且 `obj+0x1A & 8`（`0x40C623`） | u64 `obj+0x1F10`（**随机数种子**） |
| 0x40 | 每 80 帧，另有 `+0x4A0`、`+0x548` 条件（`0x40C69D..0x40C6E2`，未细查） | vec3 `obj+0x1540`（移动目标点，M） |
| 4 | 只在消息 6 里 | u64 `obj+0x490`（**随机数状态**） |

周期（`0x40C551..0x40C5BF`）：`+0x2011` 为 0 时 **40 帧**（`0x40C558 mov eax, 0x28` 经 `cmove`），置位时 **90 帧**（`0x40C55F mov ecx, 0x5A`）；
`+0x1410 == 0` 且 `+0x1520 > 0` 时 12；`+0x1410` 为 1 或 2 且 `+0x1520 > 0` 时 **3**；`+0x2011` 且 `+0x1520 > 0` 时至少 9。按 60 fps，**静止时最长 1.5 秒
才校正一次位姿**。（H 数值；上一版把 40/90 的条件写反了 / M：`+0x1410`、`+0x1520` 是 AI 模式与「有目标在动」）。本分支可缩短，见 §8.3。

**读（`0x408400`）**只在 `NetObj+8 & 1`（别人的）时执行，把上表写回同一组字段。远端副本照常跑 AI 和物理；InsectBase slot 4（`0x4A8FD0`）在远端用
`obj+0x11D0` 的修正量和 `+0x1210/+0x1218` 收到的动画参数（`0x4A9400`、`0x4A94E3`）软拉，不外推。（H 代码 / M 语义）

### 2.3 其它敌人（M）

NetObj 写/读槽：HumanoidBase / EDF6_Martian `0x477340/0x46A1B0`，MonsterBase / Monster501 `0x4BE400/0x4B7CE0`，UfoSmall507 `0x530BA0/0x52BBD0`，
DragonSmall `0x3384E0/0x3328A0`；Nephila `0x4E1F00/0x4DDEB0`、Berserker_TypeA `0x53EF80/0x53CAD0`。逐类的掩码没有逐条读，只做了一项检查：
**读槽里出现 `+0x490`（随机数状态）的只有虫类（Spider `0x4365A0`、Bee `0x41D6A0`、Ant 经消息 6）和 Nephila（`0x4DDEB0`）**，见 §4.3。

## 3. AI 在哪台机器跑

- **每台机器都跑**。没有任何一处让远端副本停掉 AI；只有个别决策点按 `+0x128 & 1` 分流。（H：GiantAnt slot 56/57 `0x409860/0x409740`、InsectBase slot 4
  `0x4A8FD0` 都只在少数分支判断拥有者）
- 例：MonsterBase 族 `0x4ABD00`：本机拥有时用 `obj+0x490` 推一步 LCG 决定 `obj+0x868 ∈ {1,2,3}`；**远端副本不掷骰子**，取网络收来的
  `obj+0x1D30` 写进 `+0x868`，再把 `+0x1D30` 置 `0x8FFFFFFF`（H）。这类决策原版就是拥有者权威。
- 虫类受击反应：slot 47 `0x40AA60` 设 `obj+0x1EE0 = 1/2`，slot 56 `0x409860` 在会话中**不判拥有者**就发消息 8（u8）/ 9（vec3），接收端
  （`0x40BB10`）本机拥有也照收。即受击反应由「被打的那台机器」广播给所有人。（H 代码 / M 语义；属于伤害，归 W3）

## 4. 随机数

### 4.1 每对象 LCG（H）

`x = x * 0x5D588B656C078965 + 0x269EC3`，状态在 `obj+0x490`（另有 `obj+0x3E8`）。常量在 EDF.dll 里有约 640 处，敌人 AI 大量直接内联。

### 4.2 种子（H）

GameObjectBase 构造 `0x545670`：
- **在会话中**（`0x545AE2` 调 `0x7748F0`）：`r8 = (|pos|² × k + 加权变换分量) 截断 + GameStatus+0x14FCC`；`obj+0x3E8 = r8 + 0xDEADBEEF`、
  `obj+0x490 = r8 + 0xBEEFDEAD`（`0x545B67..0x545B94`）。
- 不在会话：全局 LCG `0x1F54128`（`0x546448..0x546479`）。
- `GameStatus+0x14FCC` 在脚本生成函数里被临时加上脚本偏移、生成完恢复（`0x21560D..0x215619`、`0x215A06..0x215A11`）。

所以**联机时同一个脚本生成的敌人在每台机器上种子相同**（前提：生成变换按位相同，浮点同一代码路径——M）。没有跨机器的全局随机数同步；
也找不到脚本层的随机数原生函数（字符串里没有 `Rand` 类脚本声明）。

### 4.3 运行中的重新同步（H / M）

- 虫类：拥有者在 `0x4077D0`（`0x407D02` 判拥有者）发**消息 10**：旧种子 `+0x1F10` 与当前状态 `+0x490`，然后 `+0x490 = LCG(+0x1F10)`；
  接收 `0x40BBBC..0x40BC3E` 同样换种子并推一步。消息 10 只在远端副本上生效（`0x40BB77..0x40BB80`：本机拥有时丢弃）。另有掩码 0x10（种子）、4（状态）。
- **其它敌人（Humanoid、MonsterBase、UFO、Dragon、Berserker）的复制读槽里没有 `+0x490`**（M，§2.3）：它们的随机状态只靠相同的初始种子
  保持一致，一旦某台机器多/少推一次（例如 AI 分支因位置不同走了另一条），之后的随机决定就各走各的，直到对象消失。MonsterBase 的部分决策
  （§3 `0x4ABD00`）由拥有者下发结果，弥补了一部分。本分支由拥有者定期下发，见 §8.2。
- 读槽带 `+0x490` 的类（用 NetObj vtable slot 6 扫描全部 244 个 NetworkObject 子对象 vtable 得到，H）：GiantAnt / EX `0x408400`、GiantBee / EX
  `0x41D6A0`、GiantSpider / EX `0x4365A0`、Nephila `0x4DDEB0`、EDF6_SquidSmall `0x3DEDA0`（另有 FullScreen_Fog，不是敌人）。

## 5. 目标选择：分歧点（H）

GameObjectBase::Update（slot 5 `0x54BE40`，Monster/Humanoid/Insect/UFO/Dragon/HumanBase/Transporter 等 30 余类的 slot 5 都调它）：

1. `0x54BF1D..0x54BF3F`：`+0x510` 帧计数加一，`cmp ecx, [+0x514]; jb 0x54C22C`。周期 `+0x514` 默认 **60 帧**（构造 `0x5464F2`）。
2. 到点后：脚本锁定目标 `+0x528`（`LockAttackTarget` 原生 `0x1C0D70` 写入）还活着（HP `+0x2F8 > 0`）就用它；否则调 slot 14（`+0x70`，
   GameObjectBase `0x54C4B0`）：经队伍管理器 `0x20B2978` 的 `0x5E0F20` 枚举敌对对象，回调 `0x54A3B0`（`EnumNearObjectCallback`）取
   **最近的**一个（跳过 `state(+0x39C) & ~2 != 0` 的；`+0x4A0` 时距离乘目标 `+0x47C`；当前目标距离除以 `+0x538`，GiantAnt 设 100.0，即强烈保持
   当前目标；搜索半径 FLT_MAX）。
3. `0x54C130`：写 `+0x518/+0x520`（weak_ptr）。**这一步没有任何拥有者判断，远端副本也执行**。
4. `0x54C15D..0x54C1F1`：在会话中、**本机拥有**、`+0x591` 置位、`+0x2E8` 为 0 时，发**消息 1**（slot 37 `0x54CAA0` 写目标的网络 ID，经 `0x773B50`
   发送，可靠标志 1）。接收：slot 15 `0x54D590` 消息 1 → slot 38 `0x54C900` 按 ID 查对象（`0x784C60`），`0x387550` 写 `+0x518`，查不到则清空。
   虫类的消息处理 `0x40BB10` 未处理的经 `0x4A9FF0` 交到 `0x54D590`（`0x4AA264`）。GiantAnt 构造无条件置 `+0x591 = 1`（`0x4069CC`）。

**分歧**：拥有者每 60 帧发一次自己的选择；远端副本也每 60 帧用**自己看到的**玩家位置重选一次，覆盖拥有者的选择，两者相位不同。客人机器上
本机玩家的位置是准的、其他玩家的位置延迟 90ms 以上且只软拉 5%，所以客人那边的敌人更容易「转向自己」；保持系数 `+0x538 = 1.0` 的类别
（默认值）每个周期都会在两个目标之间来回翻转。敌人朝不同目标走，最长要等到下一次位姿校正（虫类 3–90 帧）才被拉回——这就是「各玩家
看到的敌人目标和行为不一样」的直接来源。`+0x591 = 0` 的类别（多为固定物：DeiroiFoot `0x328170`、`0x411D56`、`0x4C78E9`、DropBoat `0x4F3E19` 等）
拥有者根本不发目标，远端完全各选各的。

## 6. 任务脚本与任务事件（H / M）

- 脚本 VM 每帧（vtable `0x179D230` slot 4 `0x22A340`）：**客人走 `0x224930`，房主（及单机）走 `0x21FC00`**（`0x22A361..0x22A37B` 用 IsGuest 分流）。（H）
- 房主 `0x21FC00` 求值等待中的脚本线程的条件（EventFactor_*：AllEnemyDestroy、TeamObjectCount、ObjectAreaCheck、Timer、Wait 等 32 类），
  条件满足时把线程置为运行态（`+0xF8 = 3`），并调 `0x225860`：仅房主（`0x784210`），序号 `+0x4A0` 加一，`0x7736D0` 写 `(线程键 +0x24, 序号, 0, 0)`，
  经网络管理器 `+0x15C0` 的 `0x72ED40` 发出。（H）
- 客人 `0x224930` 不求值条件，只消费收到的唤醒队列（`+0x3A8/+0x3B0`，按名字 `0x10ADA80` 找线程置运行态）。之后两边都在 `0x22A384` 的
  `0x10ADC40` 里执行运行中的线程。（H 分流与消费 / M：队列由消息接收填入，接收端没有逐条读）
- 结论：**波次推进、增援、敌人全灭、任务结束这些「等条件」的事件，原版已经是房主求值、房主广播确认**，客人不会因本地死亡计数不同而提前或
  落后推进。剩余风险：被唤醒的线程里的语句在每台机器本地执行（生成敌人等），只要脚本相同就生成相同的东西、绑定相同的 ID（§1.1）；若某台机器
  的脚本或 SGO 不同（mod 不一致），ID 就会错配。本分支不需要、也没有改这一层。
- 跟随领队（脚本 opcode 调 `0x54EC50` 写 `+0x548`，会话中经 slot 39 `+0x138` 广播，`0x2122A3..0x2122C8`）同样由执行脚本的机器广播。（H）

## 7. NetworkBullet（H / L）

- `eos::NetworkBullet` vtable `0x179E018`（slot 3 `0x765520`、slot 4 `0x22F570`）。BulletBase slot 13 `0x22F0B0`：在线任务中、子弹有网络 ID（`+0x128 != -1`）时取
  射手（`+0x120` slot 1）；**射手是本机的**才按事件发消息 0（`0x233450`，`+0xE8C & 2` 且参数低于阈值）、1（`0x2339E0`）、2（`0x2330B0`），经 `0x765570`
  发送；射手是别人的，事件 1 只在本地处理 `0x233630`。`0x22F580` 判子弹是否远端 = 射手 `+0x128 & 1`（可被 `+0xE84/+0xE85` 覆盖）。（H）
- 敌人的子弹因此由拥有者（房主）发送。**远端敌人副本自己的 AI 也会开火**（AI 不停，§3），本地生成的子弹被标为「远端子弹」；它会不会造成伤害、
  会不会和拥有者发来的子弹重复显示，取决于伤害端的远端判定，没有读到（L，归 W3 / 待真机）。

## 8. 本分支的修改

### 8.1 目标保持（只改本机，`NetFeatureEnabledLocally(WorldAuthority)`）

`[Netcode] WorldAuthority=1`（默认；集成前叫 EnemyTargets）：hook `0x54BF39`（`cmp ecx, [rdi+0x514]`，6 字节，挪进 thunk），在计数到点的帧上，若对象
在会话中、`+0x128 & 1`（别人的）、`+0x591` 置位且 `+0x2E8` 为 0（拥有者在发目标）、当前目标 weak_ptr 还活着（控制块 use 计数非 0）、目标
`state & ~2 == 0` 且 HP > 0，就把 ecx 置 0，让原版的 `jb` 跳过本帧重选。目标仍由拥有者的消息 1 更新（每 60 帧，可靠发送）。没有目标或目标已死时
照原版本地挑一个，直到拥有者的下一条消息。

- 不改任何发送内容：没装 mod 的成员照原版行为，混装房间不受影响，所以不需要协议版本门（只有本地开关）。
- 字节核对单独做（`VerifiedWorldHooks`）：对不上只关本功能、写日志，插件其余部分照常。
- 测试 `multislot/tests/networld_test.cpp`：判定表；假 GameStatus + 假对象上的处理函数（含不可读指针、开关）；把原版指令复制成函数、装 hook 后实跑，
  验证 thunk 里挪过去的 `cmp` 与原版 `jb` 的组合。`NetWorldSitesMatchEDF` 对 EDF.dll 文件核对站点字节、`jb` 目标 `0x54C22C`、计数 / 存储 / 发送条件
  的指令字节。

### 8.2 非虫类敌人的随机数同步（改线上内容，`NetFeatureActive(WorldAuthority)` 全房间门）

- **发**：拥有者在 `0x54BF39` 那个钩子里（每个对象的重选帧，即每 `+0x514` = 60 帧一次），对满足 `ShouldSyncRng` 的对象——全房间门开、在会话中、
  `+0x128` 只有 bit1（本机拥有）、队伍 `+0x314 == 1`（敌方，`0x54EE88` 读的同一个字段；M：1 是敌方来自脚本生成参数）、NetObj vtable 不在 §4.3 的
  已同步列表——每 `[Netcode] EnemyRngSyncMs`（默认 2000，最少 100）发一条：小整数**类型 14**（`0x12B5790`）+ 字节块（`0x12B5200`）
  `'R' 'S' 版本1 | u32 序号 | u64 +0x490 | u64 +0x3E8`（23 字节，`worldrng.h`），经对象自己的 NetworkObject **+0x80（`0x773DA0`）**广播（事件 7）。
- **收**：hook `0x54D79E`（`0x54D770` 内、游戏读完类型并排除 0、1 之后：`mov [rsp+0x30], rsi` 挪进 thunk，此处 `r8d = 类型 - 1`、rbx = NetworkObject、
  rdi = 流）。`r8d == 13` 即类型 14：全房间门关时只计数、不读（游戏随后 `cmp r8d,1; jne 0x54D86F` 返回，和没装钩子一样）；门开时读块（`0x12B4900`）、
  校验魔数与版本，对象是别人的（bit0）且序号比该对象上次收到的新（有符号差，可回绕；30 秒没消息的对象重新开始）才覆盖 `+0x490/+0x3E8`。
- **为什么用游戏的对象消息**（与 W3 同一通道，见 damage.md §6.3）：对象寻址直接用游戏的网络身份；加密、确认、重发、批量由游戏包控制器做，W1 的
  传输改动自动覆盖；不需要另造对象 id 映射（W1 的 SendBulk 是按成员寻址的整块消息，用来发几百个 23 字节的对象级更新反而要自己做对象表和分批）。
  游戏自己的接收（GameObjectBase 0–3、HumanBase 0、VehicleBase 4–5）和 W3（13）都不认 14：旧版本或门外的机器收到也只会忽略。
- **局限**（M）：覆盖的是「拥有者发送那一刻」的状态，远端在延迟之后才用上；它让之后的随机序列重新对齐，但不消除延迟造成的时间差（与虫类原版
  消息 10 同一思路）。哪类 AI 在哪一帧掷骰子没有逐类核实；覆盖只发生在消息处理时（游戏线程、对象更新之间），不会打断一次 AI 决策的中间。
- **带宽**（按 W1 NETTYPE 口径：每条记录计 4 字节头 + 记录长度）：类型字节 1 + 块头 2 + 23 = 26 字节负载，加事件帧里对象描述符等，约 **40 字节/条**。
  默认 2000 ms：每个非虫类敌人 20 B/s，**300 个约 6 KB/s，从拥有者（房主）到每个成员**；W6 的兴趣管理若过滤该事件类型会更少。房主上行 = 6 KB/s ×
  成员数。可在日志的 `NETTYPE` 行里看对象事件记录的增量核对；`NetLog=1` 时每 60 秒一行 `WORLD rng:` 计数（发出 / 失败 / 收下 / 过时 / 格式错 / 非远端 / 门关）。
- **测试**：消息往返与拒收、`ShouldSyncRng` 判定表、发送节流与接收序号窗口（含回绕、遗忘）、类型判别、接收钩子挪走的 rsp 相对写入在原栈帧上执行；
  对 EDF.dll 核对：`0x54D79E` 站点字节、其前的读类型与两次减一、其后对未知类型返回到 `0x54D86F`、`0x12B4BB0 → 0x12B4660`、种子写入点
  `0x545B85/0x545B94`、队伍字段 `0x54EE88`、8 个已同步 vtable 的 slot 6。发送与接收两端都要调用游戏的流与网络函数，无头的 gamenet 只有
  `MissionSync` 替身、没有任务对象，无法在那里做往返（同 damage.md §8 的理由）。

### 8.3 虫类位姿间隔（只改本机发送量，本地开关）

`[Netcode] InsectPoseFrames`（默认 30；0 或 90 = 原版；有效 3..89）：把 `0x40C558` 的 `mov eax, 0x28` 改成 `min(40, N)`、`0x40C55F` 的 `mov ecx, 0x5A`
改成 `N`，先核对两处原字节，对不上就保持原版并写日志。只影响本机拥有的虫子多久发一次位姿；接收端格式不变，所以不需要全房间门。

带宽代价（NETTYPE 口径）：一次位姿 = 掩码 1 + WalkCharacterSyncControl（标志 1 + 1 + vec3 + 压缩四元数）≈ 20–25 字节 + 4 字节记录头 ≈ 30 字节。
静止虫子在 90 帧档从 0.67 次/秒升到 2 次/秒，**每只每成员约 +40 B/s**；40 帧档从 1.5 升到 2 次/秒，约 +15 B/s。300 只静止的蚂蚁最坏约 **+12 KB/s
每成员**（房主上行乘成员数）。动起来的虫子本来就在 3/9/12 帧档，不受影响。这部分走 W1 的状态类（可丢、只留最新），带宽不够时 W1 会丢弃旧的。

## 10. 真机才能验证

1. 两机（房主 A、客人 B）同一波蚂蚁，B 站得离蚂蚁比 A 近：开关为 1 时 B 看到的蚂蚁应和 A 看到的追同一个人；为 0 时对照原版（B 端敌人常转向 B）。
   日志 `NetLog=1` 下 `WORLD target:` 行列出远端副本自己挑目标的原因（只记前 40 条）。
2. 新生成的敌人在 B 上起步是否正常（第一条消息 1 到达前仍按本地选择）。
3. 远端副本开火是否重复、伤害是否重复（§7，交 W3 一起看）。
4. 随机数同步（§8.2）：人形 / UFO 类敌人在两边的攻击动作是否更一致；`WORLD rng:` 行里「收下」应随时间增长、「过时」很少；`NETTYPE` 的增量与 §8.2 估算对得上。
5. `InsectPoseFrames=30` 时远端静止蚂蚁的跳变是否变小、NETTYPE 增量是否在 §8.3 估算之内。
